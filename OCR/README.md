# Local Verification OCR

在 macOS 的 Chrome 中，由使用者選取驗證碼圖片，在本機辨識英文與數字，再填入指定欄位的擴充功能實驗。

> **實驗結果：未達到可靠辨識的目標。**
> 專案已完成圖片選取、截圖裁切、本機 OCR 與欄位填入流程，但開發者實際使用回饋是辨識效果不佳，尚不足以成為實用的驗證碼輸入工具。此 repository 保留實作與失敗經驗，供研究及重現使用。

## 為什麼做這個專案

原本希望減少在 Mac 登入網站時，手動閱讀及輸入圖片驗證碼的步驟。預期操作是：點插件、選圖片、選欄位，確認結果後填入。辨識在本機執行，不依賴雲端 OCR 服務。

核心目標是可靠地減少手動輸入。以目前的使用回饋來看，這個目標尚未達成，因此將本次實驗記錄為失敗的原型。

## 已實作功能

- 點擊工具列圖示後，直接進入圖片選取模式；也可手動框選區域。
- 選取圖片與文字輸入欄，保存該頁配對設定。
- 支援 `A–Z`、`a–z`、`0–9`，可切換純數字模式及指定字元長度。
- 保留大小寫與前導零，提供預覽和人工修正。
- 填入前再次截圖，比較圖片是否更新；偵測到更新便停止。
- 使用本機 Web Worker 執行 OCR，重用單一 worker，預設閒置五分鐘後釋放。
- 由使用者自行確認並提交網站表單。

## OCR 如何運作

```text
點擊插件 → 選取圖片與欄位 → 截圖並裁切
    → Tesseract.js 本機辨識 → 預覽／修正
    → 再次截圖並比較 → 填入欄位
```

| 元件 | 實作 |
| --- | --- |
| 擴充功能 | Chrome Manifest V3、TypeScript |
| OCR 引擎 | Tesseract.js `6.0.1`、tesseract.js-core `6.0.0` |
| 語言模型 | `tessdata_best/eng`，浮點 LSTM，檔案約 15.4 MB |
| 引擎設定 | LSTM-only（OEM 1）、單行文字（PSM 7） |
| 圖片處理 | 原圖、放大、放大後灰階，固定三個版本 |
| 執行位置 | Offscreen document 中的 Web Worker／WebAssembly |

模型版本與來源校驗值固定在 [scripts/model-lib.mjs](scripts/model-lib.mjs)。原始辨識程式位於 [extension/src/provider.ts](extension/src/provider.ts)。

三個版本的輸出須符合所選字元種類及長度、完整字串相同，且各自 confidence 至少 70，才符合直接填入的條件；選擇預覽或未達條件時，需人工確認。三次結果一致仍可能一起辨識錯誤，confidence 也不等於正確率。

## 失敗經驗與限制

目前能確定的是：實際使用回饋不佳，但尚無標註資料集、失敗樣本分類或模型對照，無法量化正確率，也無法確認各因素的影響程度。

從目前實作可看出的限制包括：

- 本專案沒有針對目標網站圖片訓練或微調模型，也沒有針對其干擾線、字元黏連或扭曲建立專用處理。
- 三個辨識版本使用同一模型，處理僅限原圖、放大與灰階；結果一致不能當作獨立驗證。
- 開放英文字元代表允許引擎輸出英文，不代表能可靠區分 `O/0`、`I/l/1` 等相似字元。
- 改用 `tessdata_best` 後，尚無對照資料證明它改善了這個專案的真實使用效果。
- 人工修正是目前流程的一部分；若修正成本接近或超過手動輸入，便未達到原本的省時目標。

這次實驗的教訓是，應先用目標場景的圖片驗證辨識能力，再評估是否值得完成整套操作流程。若後續繼續研究，優先補足完整字串正確率、人工修正率與每次操作時間的評估依據。

其他已知限制：不支援 iframe／Shadow DOM 內元素、Chrome 內部頁面、動畫或互動式驗證。圖片與欄位必須同時完整可見；捲動、切換分頁或欄位重建可能取消操作。嚴格像素比較可能因渲染差異拒絕填入，網站也可能拒絕或還原程式填入的值。

## 安裝與重現

需求：macOS、Chrome 120 或以上、Node.js 24 或以上。首次安裝需連線下載引擎、模型及測試資源。

下載 repository 後，在專案根目錄執行：

```sh
npm run setup
```

也可在 Finder 雙擊 **安裝 Chrome 插件.command**。不需要先執行 `npm install`；專案使用 Node.js 內建工具建置，另由資源安裝器下載固定版本的相依檔案。

安裝成功後：

1. 開啟 `chrome://extensions`，啟用「開發人員模式」。
2. 點「載入未封裝項目」，選擇專案中的 `dist` 資料夾。
3. 固定「本機驗證碼圖片助手」到工具列。
4. 在一般網頁點插件，依序選取圖片和輸入欄。
5. 選擇字元模式，先用「先預覽」檢查或修正結果，再填入。

已安裝的版本更新後，須重新建置、在擴充功能頁重新載入，並重新整理網站。`dist-ui` 僅供介面開發，沒有 OCR 能力。下載失敗時可查看本機 `reports/setup-latest.log`，修正連線問題後重跑安裝。

## 開發與驗證

| 指令 | 用途 |
| --- | --- |
| `npm run setup` | 安裝資源、測試、建置並驗證完整套件 |
| `npm test` | 執行單元／模擬整合測試，不需模型下載 |
| `npm run assets -- --fixtures` | 下載並校驗 OCR 及測試頁資源 |
| `npm run build` | 建立完整 `dist`，資源缺少時失敗 |
| `npm run verify` | 檢查打包資源、模型、雜湊與權限 |
| `npm run build:ui` | 建立沒有 OCR 的介面測試版本 |
| `npm run fixture` | 啟動本機測試頁 |
| `npm run test:browser` | 執行瀏覽器 DOM／React／Vue 測試 |

執行 `npm run fixture` 後開啟 `http://127.0.0.1:8765`。測試頁提供 `001234`、`A7b3Z9`、圖片刷新、Canvas、React／Vue 欄位等人工案例；這些案例不足以代表真實驗證碼。

評估 OCR 時，依 [dataset.example.json](tests/data/dataset.example.json) 準備本機 PNG／JPEG 與區分大小寫的字串標註，再執行：

```sh
npm run evaluate -- /path/to/dataset.json 20
```

範例只提供資料格式，沒有附圖片。報告輸出至 `reports/evaluation.local.json`，包括完整字串正確率、需修正率、失敗率與冷／暖啟動延遲。此工具測量辨識 provider，未涵蓋擴充功能從截圖到填入的完整時間；CPU／記憶體須另行量測。

歷史開發與驗證紀錄見 [reports/VALIDATION.md](reports/VALIDATION.md)。建置採用 Node.js 的 TypeScript 語法移除功能，未執行完整靜態型別檢查。

## 專案結構


Repository 保留重現實驗所需的原始碼、測試、工具與驗證紀錄；目前行為以程式碼及本 README 為準。

## 資料處理

執行 OCR 時，擴充功能截取目前可見分頁並在本機裁切，模型只處理裁切後的圖片。程式未實作圖片上傳、辨識歷史保存或帳密讀取；完成或取消後清除本次暫存。

本機設定保存網站 origin、路徑、元素 selector、框選範圍與辨識偏好。權限為 `activeTab`、`scripting`、`storage`、`offscreen`；安裝時需下載相依資源，辨識時使用打包在擴充功能內的檔案。
